# 量化开发原则与 coordinator 协作规范

本文是采用 Herdr Projects coordinator 工作流开展量化交易项目的工程基线。规划工作、分配任务、实施变更和审核交付时，均应遵循本文。

目标是在保证量化正确性的同时，使系统易于理解、可复现且便于调整。通过明确的契约、仓库指令和可执行检查，让项目知识能够跨越单次 agent 对话持续保留。

## 1. 确立领域不变量

实现一项能力之前，先明确其业务含义、输入、输出、失败行为和适用的不变量。让这些要求贯穿架构、任务说明、实现和验收检查。

### 保持时点正确性

每个决策只能使用决策时刻已经可用的信息。区分观测的事件发生时间与系统实际能够获取该观测的时间。对于影响结果的因素，明确时区、交易日历、发布延迟、数据修订策略，以及相同时间戳下的处理顺序。

这些规则适用于原始数据、标的池成员、公司行动、特征、预处理、模型产物、组合构建和执行。历史查询必须选择当时可用的数据版本。模型产物的使用时间，不得早于根据其输入和训练过程实际能够生成该产物的时间。

事件驱动架构可以表达这些约束，但仅有事件处理并不能保证时点正确性。在数据接口和决策边界强制执行可用性规则。所需的时间信息缺失或存在歧义时，必须拒绝继续执行。

直接检验因果性。修改决策之后才变得可用的数据，不得改变该决策。相关场景应覆盖数据修订、延迟发布和边界时间戳。

### 隔离训练、验证与最终评估

在模型选择之前，声明时间划分及其用途。对于每一折，只能在该折允许使用的训练数据上拟合需要学习的预处理步骤和模型参数。验证结果可以在已声明的规程内指导选择。最终样本外评估必须与该选择过程隔离。

考虑标签重叠和未来收益计算区间。存在相应依赖时，采用样本剔除（purging）或隔离期（embargo）。每份结果都要记录划分边界、拟合窗口和选择规程。不得将已经用于评估的留出集悄悄重新当作从未使用过的测试集。

### 明确数值语义

在物理接口处定义单位、币种、价格口径、数量口径、数值表示和取整策略。明确转换发生的位置，防止重复转换或非预期的精度损失。

根据领域需求选择表示方式。为订单明确最小价格变动单位和最小交易单位约束，为浮点计算设定有依据的误差容限。规格缺失、数值无效或必需输入过期时，不得用任意默认值代替。

在入口处解析和校验外部数据及配置。可以使用 Pydantic 模型、冻结的数据类或等价的类型化契约完成这些检查。如果隐式类型转换会掩盖错误，就使用严格解析。输入只规范化一次，内部代码随后依赖已校验的契约。

## 2. 明确设计依赖关系与数据流

对于具有无环依赖的研究和计算流程，使用有向无环图（DAG）建模。每个节点必须声明输入、输出、依赖、配置，以及相关的历史数据或状态需求。从依赖关系推导执行顺序，不要另行维护手工执行序列。

对于执行生命周期和其他反馈过程，使用状态机或显式状态转换。不要把实盘交易系统的全部行为强行放进 DAG。

按照不同的变更原因拆分模块。数据接入、特征计算、模型拟合、组合构建、执行和评估都需要明确的职责归属。不要仅因为某个工作流会同时使用这些能力，就把它们集中到同一个类或模块。

在可行时，让领域计算独立于文件、环境变量、系统时钟和券商 API。显式传入所需的输入和状态。将外部副作用放在适配器之后，在明确的应用入口完成组装。

在有实际意义的外部边界应用依赖倒置。优先使用组合而非继承。只有实际存在变化需求时，才引入工厂、注册表或其他扩展机制。运用 KISS、DRY 和 Clean Code 原则降低复杂度，同时保留业务含义不同的概念之间的区别。

## 3. 保持回测与实盘的语义一致

回测和实盘必须共享核心决策逻辑与领域契约。通过明确的适配器隔离数据交付、时钟行为、持久化、券商连接和模拟执行。

明确两种模式必须产生等价决策的条件。对延迟、部分成交、滑点、拒单和数据修订等不可避免的差异进行建模。不要用未经验证的等价假设掩盖这些差异。

如果同时存在向量化批量计算和增量处理，明确它们共享的状态与历史数据契约。在信息和初始状态相同的情况下，验证输出等价。契约要求精确一致时，进行精确比较；否则，应在评估结果之前声明数值容差并说明依据。

## 4. 使结果可复现、运维可检查

记录实际生效的配置、代码修订版本、输入数据集名称及修订号、模型产物、数据划分定义和随机性来源。保留复现已报告结果所需的产物。声明妨碍精确复现的外部依赖或非确定性依赖。

为生产输入指定负责方、新鲜度上限，以及缺失或过期时的明确行为。为具有副作用的工作流定义安全的重试和重启行为。保留足够的状态，以区分已完成的动作与中断的尝试。

每项可操作的业务能力都必须有对应的 CLI 工作流。CLI 命令保持轻薄，将业务行为交给可复用的应用逻辑。明确输入、输出、退出行为和副作用。根据真实用例添加命令，不要为每个内部函数创建无人使用的命令。

CLI 为人和 agent 提供一致的方式，用于运行系统、检查状态、复现结果和展示验收场景。

## 5. 将仓库组织为持久化项目记忆

为每份契约、规则和决策指定唯一的权威位置。将持久知识纳入版本控制，并在任务说明中引用。将临时任务状态与长期领域知识分开。

以下结构是目标职责分布。根据现有包结构调整路径。这些目录描述预期的职责归属；本文不要求 agent 创建空包，也不要求在没有具体任务时重组一个正常工作的项目。

```text
AGENTS.md                 仓库级不变量与工作规则
schemas/                  权威数据契约与校验
  AGENTS.md               契约变更的局部规则
core/                     领域计算与流水线组装
  README.md               职责、数据流、依赖方向
  AGENTS.md               局部领域约束
cli/                      命令入口与应用接线
  AGENTS.md               命令契约与验证规则
adapters/                 外部数据、存储、时钟与券商
docs/
  architecture.md         系统拓扑与模块边界
  decisions/              已接受的架构决策及其理由
  verification.md         不变量及其对应检查
  tasks/                  任务说明、证据、交接与待解问题
tests/                    行为验证与契约验证
```

`schemas/` 包含关于数据形状、时间可用性、单位、校验和相关兼容性规则的可执行契约。领域语义要求不可变时，保持领域对象不可变。运行时不可变并不意味着 schema 永远不能变化。显式演进契约，并同步迁移其使用方。

`core/` 包含实际的领域逻辑与组装，并有明确的内部边界。其文档解释代码实际实现的结构。`core` 这一名称不意味着可以放入无关职责或不受限制地导入模块。

`cli/` 负责用户交互和命令组装。`adapters/` 负责外部副作用。两者都不得重复实现领域计算。

`docs/architecture.md` 解释跨模块关系。决策记录说明重要选择的理由，并标明已被取代的决策。任务记录保存当前假设、进度、证据和未完成工作。不要让任务日志变成另一套相互竞争的架构规范。

当文档、契约和实际行为不一致时，根据已批准的业务需求识别并解决差异。实现缺陷不能重新定义预期契约。

## 6. 在适用范围内提供上下文

仓库级指令应足够简短，便于每个 agent 使用。将局部要求放在其约束的代码附近。局部指令可以细化更广泛的规则，但不得悄悄削弱领域不变量。

对于每项重要不变量，记录其权威定义、受影响组件、验证命令和失败含义。引用该定义，不要在多个指令文件中复制其措辞。

coordinator 必须根据当前仓库产物组装任务上下文。worker 在实现前必须阅读适用的指令与契约。如果任务依赖尚缺失的业务信息，应说明缺口，并且只继续开展不依赖该问题答案的独立工作。

交接或重置上下文之前，记录当前修订版本、已完成变更、验证证据、未解问题和下一步动作。新 agent 应能根据这些记录继续工作，无需重建整段对话。

## 7. 明确 coordinator 与 worker 的职责

coordinator 负责工作拆解、依赖规划、任务分配、共享契约决策、集成和验收审核。worker 负责边界明确的变更，并提供证据证明变更满足所分配的要求。

当项目需要独立的范围和执行过程时，每个仓库使用一个项目 coordinator。跨项目发现应报告给对应的 coordinator。这些发现并不授权 agent 编辑其他仓库。

向每个 worker 提供的任务说明必须包含：

- 业务目标与具有代表性的领域场景。
- 相关契约、指令和架构决策。
- 允许的范围，以及文件或模块的归属。
- 对其他任务的依赖，以及共享接口决策。
- 可观测的验收标准及其验证命令。
- 必须更新的项目记忆，以及预期的交接产物。

通过独立的文件归属或隔离的 worktree 分开并发写入者。为共享契约和集成变更指定唯一负责人。在依赖这些契约的 worker 基于不兼容假设开展实现之前，先协调契约变更。

worker 不得绕过检查、削弱校验、通过修改预期结果掩盖缺陷，或根据未执行的测试声称完成。必须披露简化处理、未解决的失败和偏离任务说明的情况。更大范围的变更如果影响其他 worker 的契约，必须交回 coordinator 协调。

coordinator 必须检查集成证据。worker 的完成报告是审核输入，本身不足以证明正确性。使用当前已安装版本的 Herdr Projects 能力，并在依赖命令前验证其可用性。不要假设其他版本的示例命令在当前版本同样可用。

## 8. 通过可执行检查演进架构

定义目标架构，并以可验证的增量逐步推进。每个增量必须交付一项可观测能力，或强制落实一项必要边界。避免没有实际依据的抽象；临时兼容层必须有明确的使用方和移除计划。

使用架构适应度函数，即对架构属性进行的可执行检查。相关检查包括允许的导入关系、依赖环、契约兼容性、时点行为、可复现性和不同执行模式之间的等价性。

记录每项检查的范围与局限。依赖检查通过不代表量化正确性成立。单元测试通过也不代表实际操作流程已经可用。

根据变更及其风险选择验证方式。使用行为测试、边界场景、CLI 验收场景和相关集成检查。适用时，扰动决策时刻之后的输入数据，或注入会触发失败的输入，以证明检查能够识别被禁止的行为。修改输入，不修改代码：不使用变异测试或对抗式审核循环。

## 9. 声明完成之前必须提供证据

对于每项任务，worker 和 coordinator 必须确认：

- 所要求的业务行为能够通过预期入口正常执行。
- 适用的时间、统计和数值不变量成立。
- 变更保持已声明的依赖边界与职责归属边界。
- 已针对交付的修订版本运行相关检查，并记录结果。
- 契约、架构和操作文档与交付行为一致。
- 剩余限制、未经验证的行为和阻塞依赖均已明确披露。

如果实现改变了契约、工作流或架构决策，应在同一次变更中更新持久化项目记忆。证据必须足够具体，使另一位工程师或 agent 能够重复验证。
