# 量化开发原则与 coordinator 协作规范

这份指导适用于通过 Herdr Projects coordinator 协作开发的量化交易项目。无论是规划架构、分配任务、编写代码，还是审核交付，都应以这里的原则为依据。

我们希望系统在量化逻辑上正确，也容易理解、复现和演进。为此，需要把项目知识写进接口契约、仓库指令和自动化检查，让这些知识在更换 agent 或重置对话后仍然有效。

以 **Check** 表示自动化结构检查，**Test** 表示行为测试，**Review** 表示工程判断。在 `docs/verification.md` 中记录命令或审查证据；交付细节参照 `new-project-skeleton-efficiency-and-delivery.zh-CN.md`。[Check / Review]

## 1. 明确必须始终成立的领域约束

实现一项功能前，先说明它解决什么业务问题、接收什么输入、产生什么输出，以及失败时如何处理。同时列出必须始终成立的领域约束（invariants），并将其落实到架构、任务说明、代码和验收中。

### 保证 point-in-time 正确性，防止 look-ahead bias

Point-in-time（PIT）的核心要求是：每次决策只能使用当时已经可以获得的信息。数据描述的事件发生时间（event time），与系统实际能够获得这条数据的时间（availability time）必须区分。时区、交易日历、发布延迟、数据修订，以及同一时间戳下的处理顺序，只要影响结果，就必须明确约定。

PIT 约束覆盖整条链路：原始数据、标的池（universe）成员、公司行动、特征、预处理、模型产物、组合构建和交易执行。历史查询必须返回当时可见的数据版本。模型也只能在其所需数据已经可用、且训练过程能够完成之后参与决策。

事件驱动架构（event-driven architecture）有助于表达这些约束，但采用事件驱动并不自动消除前视偏差（look-ahead bias）。数据接口和决策入口必须检查信息是否已经可用。必要的时间信息缺失或有歧义时，应采用 fail-closed 策略，停止执行。

通过行为测试验证这条因果约束：修改某次决策之后才可用的数据，不应改变该次决策的结果。测试应覆盖数据修订、延迟发布和时间边界。

在唯一权威边界完成可用性标准化与打标，拒绝重复应用。将标准化与可反复执行的 as-of 查询分开。记录每次查询的截点、可用性规则和选中版本；shift 标记不能代替 PIT 语义。[Check / Test]

为每个节点声明修订传播与重算规则。区分有限窗口失效、递归重放和模型重拟合；仅凭 lookback 不足以判断。[Check / Test]

### 隔离训练、验证与最终评估

开始模型选择之前，明确训练集、验证集和最终评估集的时间范围与用途。在交叉验证的每个 fold 中，预处理里需要拟合的部分和模型参数，都只能使用该 fold 允许的训练数据。验证集可以按预先约定的流程用于模型选择，最终的 out-of-sample 评估必须与这个选择过程隔离。

划分数据时，要考虑标签之间是否重叠，以及未来收益的计算区间是否跨越分界点。必要时使用 purging 和 embargo，剔除存在信息重叠的样本或设置隔离期。每份结果都要记录 split 边界、拟合窗口和模型选择流程。已经参与评估的 holdout，不能再被当成未使用过的测试集。

### 明确数值语义

在数据读写、模块交接和订单发送等实际接口处，明确单位、币种、价格与数量口径、数值类型和取整规则。每项转换都要有唯一、明确的位置，防止重复换算或无意的精度损失。

根据业务含义选择数值表示。订单要明确 tick size 和 lot size 约束，浮点计算要设定有依据的 tolerance。规格缺失、数值无效或必需输入过期时，不得用任意默认值代替。

在入口处解析和校验外部数据及配置。可以使用 Pydantic model、frozen dataclass，或具有同等约束能力的类型定义完成检查。如果隐式类型转换会掩盖错误，就使用严格解析。输入只做一次标准化处理，内部代码随后依赖已经通过校验的契约。

显式提供业务语义参数，绝不用零或哨兵值填充缺失。内部不重复解析类型，但在计算产生非有限值、约束违反或非法转换的位置检查。在契约与算子文档中说明张量轴序、单位、自由度和缺失值传播。[Check / Test / Review]

## 2. 明确设计依赖关系与数据流

对于具有无环依赖的研究和计算流程，使用有向无环图（DAG）建模。每个节点必须声明输入、输出、依赖、配置，以及相关的历史数据或状态需求。根据依赖关系计算拓扑顺序，不要额外维护一份手工排列的执行顺序。

为节点声明空间耦合轴（`per-instrument` 或 `cross-sectional`）、分组和允许的输入。禁止沿标的轴盲切横截面算子；分布式归约须声明合并规则并通过等价性测试。[Check / Test]

对于执行生命周期和其他反馈过程，使用状态机或显式状态转换。不要把实盘交易系统的全部行为强行放进 DAG。

按照“什么变化会导致这个模块需要修改”来划分模块。数据接入、特征计算、模型拟合、组合构建、执行和评估都需要明确的职责归属。不要仅因为某个工作流会同时使用这些能力，就把它们集中到同一个类或模块。

尽量让领域计算不直接读取文件、环境变量或系统时钟，也不直接调用券商 API。所需数据和状态通过参数传入。文件读写、网络调用等外部操作交给 adapter，在明确的应用入口统一组装。

在确有必要的外部接口处应用依赖倒置（dependency inversion）。优先使用组合而非继承。只有实际存在变化需求时，才引入工厂、注册表或其他扩展机制。运用 KISS、DRY 和 Clean Code 原则降低复杂度，同时保留业务含义不同的概念之间的区别。

允许已声明、无环的公开接口依赖；拒绝私有导入和未声明的数据访问。实际边界可支持仅有一个实现的窄接口；注册表和通用扩展须有具体用例后再添加。[Check / Review]

## 3. 保持回测与实盘的语义一致

回测与实盘必须共享核心决策逻辑和领域契约。数据接入、时钟、持久化、券商连接和模拟成交的差异，由各自的 adapter 处理。

明确两种模式必须产生等价决策的条件。对延迟、部分成交、滑点、拒单和数据修订等不可避免的差异进行建模。不要用未经验证的等价假设掩盖这些差异。

将含状态节点定义为 `(inputs_t, state_{t-1}, params) -> (alpha_t, state_t)`。区分业务输出与充分状态；Alpha 或系数本身可能不足以继续计算。Batch、Backfill 与 Step 共享数学、历史和状态契约，不必调用同一个函数。[Check / Test]

重跑 `t` 时，固定只读加载同一个已确认的 `state_{t-1}`。将新的不可变 `state_t` 与输出引用原子提交。禁止原地推进状态或从未确认的尝试恢复递推。[Check / Test]

将端到端幂等契约应用于 Alpha 回测与实盘日更（Daily Production）。将只追加的尝试与逻辑视图分开，视图键为 `(node_id, decision_time, vintage, config_digest)`。该键固定引用输入、实现、schema 和初始状态版本。匹配重试直接短路或原子指向内容完全一致的产物；来源或内容冲突时拒绝。约束行键唯一，防止重复行、权重或发布副作用。[Check / Test]

在预热期、PIT 视图、参数和初始状态相同时，对比 Batch、Backfill 与 Step 的重叠输出和状态，包含分段与重跑。固定实现和数值环境，保证重复运行的确定性。整数和离散决策精确比较；比较不同实现或环境前说明浮点容差依据。单独测试阈值、排序、取整和订单后果。不得用容差静默替换有冲突的已发布产物。[Test / Review]

按稳定键（例如 `(seed, node_id, decision_time)`）派生随机流，并采用规范条目顺序或稳定条目子键。禁用依赖任务顺序、分区或此前尝试的全局 RNG。[Check / Test]

保持 As-Traded 不可变。按原截点与固定的输入、代码、配置、模型和状态版本精确复现已发布信号。迟到或修订重算写入新 `vintage`。发布全程携带幂等键；未授权变更以独立的 `business refusal` 退出码拒绝。[Check / Test]

## 4. 使结果可复现、运维可检查

记录实际生效的配置、代码修订版本、输入数据集名称及修订号、模型产物、数据划分定义和随机性来源。保留复现已报告结果所需的产物。声明妨碍精确复现的外部依赖或非确定性依赖。

仅对规范序列化后的参数与实际生效配置计算哈希（`config_digest`）。禁止对原始或派生数据集、行或分区内容计算哈希或校验和，包括把数据塞进配置后间接哈希。数据集与状态快照使用不可变的显式版本、分区、schema 和来源关系。允许记录 Git commit 标识。[Check / Review]

缓存绑定输入、实现、schema、参数、模型和初始状态版本。通过契约、唯一键、行数、时间覆盖、来源及验收时必要的内容对照验证数据。避免每次运行重扫历史；这些检查不提供内容校验和级别的完整性保证。[Check / Test / Review]

为生产输入指定负责方、新鲜度上限，以及缺失或过期时的明确行为。为具有副作用的工作流定义安全的重试和重启行为。保留足够的状态，以区分已完成的动作与中断的尝试。

说明远端接受动作后、本地记录成功前的恢复规则。按稳定动作标识对账，再重试状态不明的动作。恢复记录只追加；代码回滚不撤销外部副作用。[Test / Review]

每项需要由人或调度器执行的业务能力，都必须有对应的 CLI 工作流。CLI 只负责解析参数、调用应用逻辑和呈现结果，业务实现应可复用。明确输入、输出、退出行为和副作用。根据真实用例添加命令，不要为每个内部函数创建无人使用的命令。

CLI 为人和 agent 提供一致的方式，用于运行系统、检查状态、复现结果和展示验收场景。

CLI 写入默认 Dry-run，必须显式提供 write 标志。错误处理保留 `business refusal` 的独立退出码。有明确理由的调度器直调，须复用同一应用服务和契约。[Check / Test / Review]

## 5. 将仓库组织为持久化项目记忆

为每份契约、规则和决策指定唯一的权威位置。将持久知识纳入版本控制，并在任务说明中引用。将临时任务状态与长期领域知识分开。

下面的目录树说明各类代码和知识应放在哪里。路径可以根据现有项目调整。它不是要求 agent 立即创建空包，也不意味着可以在没有具体任务时重组一个正常运行的项目。

```text
AGENTS.md                 仓库级领域约束与工作规则
schemas/                  权威数据契约与校验
  AGENTS.md               契约变更的局部规则
core/                     领域计算与流水线组装
  README.md               职责、数据流、依赖方向
  AGENTS.md               局部领域约束
cli/                      命令入口与应用组装
  AGENTS.md               命令契约与验证规则
adapters/                 外部数据、存储、时钟与券商
docs/
  architecture.md         系统拓扑与模块边界
  decisions/              已接受的架构决策及其理由
  verification.md         领域约束及其对应检查
  tasks/                  任务说明、证据、交接与待解问题
tests/                    行为验证与契约验证
```

`schemas/` 保存可执行的数据契约，包括数据结构、availability time 规则、单位、校验规则及兼容性要求。业务含义要求对象不可变时，使用不可变对象。但对象在运行时不可变，不代表 schema 永远不能修改。schema 的演进必须明确，并同步迁移调用方。

`core/` 保存实际的领域逻辑和流程组装代码，内部也必须有明确边界。文档要解释代码真实采用的结构。不能因为目录名叫 `core`，就把所有难以归类的代码放进去，或任意导入其他模块。

`cli/` 负责命令行交互与命令组装，`adapters/` 负责文件、网络等外部操作。两者都不应重复实现领域计算。

`docs/architecture.md` 解释跨模块关系。决策记录说明重要选择的理由，并标明已被取代的决策。任务记录保存当前假设、进度、证据和未完成工作。任务日志中不要再维护另一套架构定义。

当文档、契约和实际行为不一致时，根据已批准的业务需求识别并解决差异。实现缺陷不能重新定义预期契约。

## 6. 按职责范围组织 agent 的上下文

仓库级指令只保留所有 agent 都需要知道的内容，局部要求放在相关代码附近。局部指令可以补充细节，但不能削弱全局的领域约束。

对于每项重要领域约束，记录其统一定义、受影响组件、验证命令和失败含义。引用该定义，不要在多个指令文件中复制其措辞。

coordinator 必须根据仓库中的最新文件组装任务上下文。worker 在实现前必须阅读适用的指令与契约。如果任务依赖尚缺失的业务信息，应说明缺口，并且只继续开展不依赖该问题答案的独立工作。

交接或重置上下文之前，记录当前修订版本、已完成变更、验证证据、未解问题和下一步动作。新 agent 应能根据这些记录继续工作，无需重建整段对话。

持久化长任务的依赖、输入版本、产物引用、检查点、重试规则和阻塞项。根据已验证产物恢复。重复唤醒和重试不得重复提交、发布或记账。[Check / Test]

## 7. 明确 coordinator 与 worker 的职责

在满足正确性与验收要求的前提下，最小化端到端完成时间。计入分解、上下文传递、协调、集成和验证开销。快速判断规模，不要仅为给小任务分类而编写长计划。[Review]

| 任务 | 执行方式 | 落实方式 |
|---|---|---|
| 范围明确、依赖少的小任务 | 当前 agent 直接执行，避免委派和调度开销 | Review |
| 具有可独立执行部分的中型任务 | 预计并行收益超过协调成本时才使用 subagent；分派前明确输入、输出、归属与验收标准 | Review |
| 大型或长周期任务 | 建立包含依赖、交付物和关键路径的显式任务 DAG；结合可用的 workflow、goal、cron、loop 能力持久化推进 | Check / Review |

将 agent 任务 DAG 与平台计算 DAG、执行状态机分开。依赖通过验收后才释放任务；优先推进关键路径，按归属和集成能力限制并发。[Check / Review]

| 能力 | 职责 | 落实方式 |
|---|---|---|
| Workflow | 执行可重复步骤，管理状态转换、重试、恢复与产物交接 | Check / Test |
| Goal | 保存长期目标、完成标准、阶段进度与阻塞项 | Check / Review |
| Cron | 在未来时点唤醒工作或周期检查外部条件；不得用调度时间代替依赖就绪判断 | Check / Test |
| Loop | 按可测量进展迭代，声明退出条件、迭代次数或时间预算，以及无进展时的停止规则 | Check / Test |

确认工具和命令可用；必要时采用可执行的替代方案并披露限制。范围扩大时升级执行方式；协调成本超过收益时合并任务或降低并发。工作流迭代不授权多轮对抗评审。[Check / Review]

coordinator 负责工作拆解、依赖规划、任务分配、共享契约决策、集成和验收审核。worker 负责边界明确的变更，并提供证据证明变更满足所分配的要求。

当项目需要独立的范围和执行过程时，每个仓库使用一个项目 coordinator。跨项目发现应报告给对应的 coordinator。这些发现并不授权 agent 编辑其他仓库。

向每个 worker 提供的任务说明必须包含：

- 业务目标与具有代表性的领域场景。
- 相关契约、指令和架构决策。
- 允许的范围，以及文件或模块的归属。
- 对其他任务的依赖，以及共享接口决策。
- 能从实际行为判断的验收标准及其验证命令。
- 必须更新的项目记忆，以及预期的交接产物。

通过独立的文件归属或隔离的 worktree 分开并发写入者。共享契约和集成变更都应有唯一负责人。在依赖这些契约的 worker 基于不兼容假设开展实现之前，先协调契约变更。

worker 不得绕过检查、削弱校验、通过修改预期结果掩盖缺陷，或根据未执行的测试声称完成。必须披露简化处理、未解决的失败和偏离任务说明的情况。更大范围的变更如果影响其他 worker 的契约，必须交回 coordinator 协调。

coordinator 必须检查最终集成版本的实际结果和验证证据。worker 的完成报告或分支上通过的测试只是审核输入，不足以证明集成后的正确性。使用当前已安装版本的 Herdr Projects 能力，并在依赖命令前验证其可用性。不要假设其他版本的示例命令在当前版本同样可用。[Check / Test / Review]

## 8. 通过可执行检查演进架构

定义目标架构，并通过每一步都可验证的变更逐步推进。每个增量必须交付一项可观测能力，或强制落实一项必要边界。避免没有实际依据的抽象；临时兼容层必须有明确的使用方和移除计划。

分阶段设置门禁：探索须满足 PIT、显式语义、划分隔离、版本和基本参考检查；可复用组件增加稳定契约、状态恢复、独立参考和预算；生产前增加发布、对账、监控、恢复和回滚证据。保留底座 Day-zero 门禁，不把整套部署流程施加给每个假设。[Check / Test / Review]

使用 architectural fitness functions，把架构要求变成可执行检查。例如，检查 import 是否符合分层、是否存在依赖环、契约是否兼容，以及 PIT、可复现性和不同运行模式的等价性是否成立。

记录每项检查的范围与局限。依赖检查通过不代表量化正确性成立。单元测试通过也不代表实际操作流程已经可用。

根据变更及其风险选择验证方式。使用行为测试、边界场景、CLI 验收场景和相关集成检查。必须执行未来输入扰动测试。必要时注入非法输入，或在声明的失败边界中断执行，以验证 PIT 和幂等守卫。不使用代码变异测试或多轮对抗评审循环。[Test / Review]

必须覆盖同日重跑、崩溃恢复，以及完整 Batch 对比分段 Batch 接逐日 Step（含重跑）。按第 3 节数值契约检查输出、状态、重复度、权重和发布次数；详细场景见启动文档。[Test]

## 9. 声明完成之前必须提供证据

对于每项任务，worker 和 coordinator 必须确认：

- 所要求的业务行为能够通过预期入口正常执行。
- 适用的时间、统计和数值方面的领域约束成立。
- 变更保持已声明的依赖边界与职责归属边界。
- 已针对最终集成版本运行相关检查，并记录命令、环境和结果。[Check / Test]
- 契约、架构和操作文档与交付行为一致。
- 剩余限制、未经验证的行为和阻塞依赖均已明确披露。

如果实现改变了契约、工作流或架构决策，应在同一次变更中更新持久化项目记忆。证据必须足够具体，使另一位工程师或 agent 能够重复验证。

验收通过后才标记完成；调度、分派和排队重试不等于完成。区分已执行检查与未来实现要求，披露未验证的生产行为。[Check / Review]
