# 新项目启动：骨架、效率与增量交付

启动新项目或重写已有系统时，使用本指导。本文与 `quant-development-and-agent-collaboration.zh-CN.md`（下文简称“原则文档”）配套；原则文档负责领域约束、依赖设计、可复现性、项目记忆与 agent 分工，本文规定具体产物、预算和交付门禁。

防止三类失败：没有契约就堆叠功能、尚未接通真实输出渠道就停止交付、上线后才补运维。使用 `schemas/` 保存契约，`core/` 承载领域计算与组装，`cli/` 提供命令，`adapters/` 处理外部副作用。

落实方式统一标记为：**Check** 表示自动结构或规则检查；**Test** 表示可执行的行为或性能测试；**Review** 表示对含义、范围或证据的审查。

## 1. 开工与上线前的交付清单

### 按工作阶段设置门禁

所有阶段都保留 PIT、严格输入、显式参数、缺失值语义和已声明的数据划分。底座清单约束第一个可复用切片；不要要求探索一个独立假设前先建完整部署框架。[Check / Review]

| 阶段 | 进入下一阶段前的要求 | 落实方式 |
|---|---|---|
| 探索实验 | 只读且版本化的 PIT 输入、代码和有效配置记录、已声明的数据划分、基本独立参考；实验输出与生产隔离 | Check / Test |
| 可复用组件 | 边界与状态契约、因果与幂等测试、可复现入口、目标规模预算 | Check / Test |
| 生产 | 完成底座和上线清单，包括发布、恢复、监控与运维归属 | Check / Test / Review |

## 2. 数据流

- **声明节点。** 记录输入、输出、计算类型（incremental、recursive 或 full history）、lookback、充分状态和耦合轴（`per-instrument` 或 `cross-sectional`，含分组键）。从计算 DAG 推导执行顺序；执行反馈留在原则文档第 2 节规定的状态机中。[Check / Review]
- **可用性只打标一次。** 每个数据集在 `schemas/` 中保存可用性规则，由唯一的规范函数应用并附加标记。拒绝重复打标或重复施加滞后。区分这次标准化与可在不同决策截点重复执行的 as-of 查询；已打标不代表全部记录在任意截点都可见。[Check / Test]
- **修订生成新版本。** 新增或修正数据生成新的不可变修订。Compaction 写出新版本；仍被引用的旧版本保持可读。逐节点声明修订影响与重算规则，包括递推状态和模型重训的传播范围；不能仅靠 lookback 推断。[Check / Test]
- **分离输出与状态。** 将含状态计算定义为 `(inputs_t, state_{t-1}, params) -> (outputs_t, state_t)`；Alpha 节点的输出为 `alpha_t`。保存计数、中心矩、Gram 矩阵或窗口缓冲等充分状态，不能只保存上次业务输出。Batch、Backfill 和 Step 共享数学与状态契约，不强制使用同一个函数实现。[Test / Review]
- **锚定恢复起点。** 只读加载已提交的 `state_{t-1}` 快照，并固定其来源关系。重跑时点 `t` 必须使用同一前序快照，不能读取已推进的 `state_t`。输出与状态一同暂存，通过一次原子 manifest 提交对外可见（第 6 节）；禁止原地推进状态。[Check / Test]
- **随机源按键派生。** 使用已声明的稳定派生方法，从 `(seed, node_id, decision_time)` 生成可复现随机流；需要时增加稳定的标的或用途子键。禁止用顺序依赖的全局 RNG、进程相关哈希、worker 顺序或分块边界决定抽样。这些是控制键，不是数据集内容哈希。[Check / Test]
- **保持 As-Traded 不可变。** 使用原决策截点、输入修订、代码、配置、模型与前序状态复现历史已发布信号。迟到数据或修正重算写入新的 `vintage`，绝不覆盖历史 As-Traded 账本。[Check / Test]
- **通过已声明接口组装。** 以明确的公开依赖或组装层传递产物。拒绝依赖环、私有接口导入和未声明的数据读取；共用 adapter 不授权高层节点绕过已声明的输入。[Check / Test]

## 3. 分层与组装

- Driver 和 runner 不进行业务算术运算；将计算移入负责该业务的领域模块。[Check / Review]
- 在边界严格解析并标准化外部数据与配置一次。内部不重复防御性类型解析，也不引入静默默认值。仍须检查计算过程中可能失效的约束，例如非有限结果、不可行解和无效状态转换。[Check / Test]
- 跨模块使用统一字段术语。缺失值按缺失表示，绝不用零或哨兵值代替。[Check / Test]
- 为已证实的变化需求或有实际意义的外部边界建立抽象。优先使用窄接口；只有实际调用方需要发现或选择实现时才加注册表。不要求必须先有两个实现才能定义必要接口。[Review]

- 共享知识由明确的模块负责。不能因为读取、过滤、回放发生在不同阶段，就把同一数据集的格式、可见性和修订规则分散到多个包。计算 DAG、模块结构、执行状态机和 agent 任务 DAG 分别定义。[Review]
- 设计 PIT 访问、发布与恢复时，先写有代表性的调用示例。存储机制、可见性检查、去重和对账由对应能力内部处理；cutoff、修订策略、授权和冲突语义保持显式。CLI 和 adapter 即使很薄，也可能承担真实的抽象转换，不能仅因代码少就删除边界。[Review]

## 4. 参数模板

- 每个算法旁放置一个不可变参数类，说明每个字段的单位与含义。[Check / Review]
- 影响业务含义的参数不设默认值。Chunk size、worker 数量等工程参数可以有默认值；影响数值结果时记录实际生效值。[Check / Test]
- 每种用途维护一份完整配置模板。按参数类校验，并检查配置节之间的一致性；环境差异使用显式 overlay，不复制整份文件。[Check / Test]
- 函数参数依次为业务输入、参数对象、keyword-only 运行时开关。不透传 `**kwargs`；多个返回值使用具名不可变记录。[Check]
- 允许对规范化后的有效参数与配置生成 `config_digest`。声明序列化、字段顺序、数值表示与哈希算法；验证等价配置产生相同指纹，取值变化导致身份变化。数据集引用可使用显式修订 ID；禁止嵌入数据集内容进行间接哈希。遵守第 6 节的数据集禁哈希规则。[Check / Test]
- 写入生产时明确指定生产环境和启用发布的值。不得提供绕过这些守卫的 force 标志。[Check / Test]

- 每个新增选项都应表达真实业务选择，或有依据的运行控制。存储和恢复机制留在对应模块内部，不向调用方暴露一组本可封装的开关。业务语义参数仍须明确；简化机制不等于替调用方悄悄选择研究政策。[Review]

## 5. 命令行接口

- 提供形如 `<tool> <domain> <action>` 的统一操作入口，保持 CLI 轻薄。调度器需要时可调用同一应用 API；不得复制领域逻辑或绕过发布守卫。[Check / Review]
- 公共选项只定义一次，各领域复用选项类型。[Check]
- 写入命令默认 Dry-run：展示计划，未显式指定 write 时不发生业务写入。报告逻辑发布键与受影响的目的地。[Test]
- 创建只追加且名称可读的运行记录（第 6 节）。恢复中断运行时追加新的尝试记录与暂存产物；绝不改写既有证据或已完成产物。新的尝试不等于新的逻辑发布。[Check / Test]
- 退出码表区分成功、可重试失败、永久失败与 `business refusal`。将业务拒绝传播到应用入口并映射为独立退出码，绝不报告为成功。[Test]
- 发布接收端必须使用幂等键。崩溃或响应不明确后，先核对接收端已提交状态再重试；不能因本地缺少成功记录就推断发布失败。拒绝未授权替换和同键冲突发布。[Test]
- 开发专用工具放在交付包与操作 CLI 之外。[Check]

## 6. 标识与运行记录

- 使用可读名称、日期、序号、修订 ID 和参数集名称标识运行与产物，禁止裸哈希目录名。区分物理尝试 ID 与逻辑发布键。[Check]
- 用 `(node_id, decision_time, vintage, config_digest)` 标识一份逻辑输出快照。在来源关系中固定节点实现、schema、输入修订、模型和初始状态；来源变化时显式更新身份版本。快照内强制行键唯一，面板数据包含标的身份，避免重跑增加重复行或双倍权重。[Check / Test]
- 通过原子条件提交或等价的接收端事务保证唯一性。相同重跑可直接短路，或原子指向内容完全相同的产物。输出与状态通过同一已提交 manifest 引用发布，读取者不得看到混合版本。同键来源或内容冲突时触发 `business refusal`；数值容差不构成替换已提交结果的授权。[Test]
- 运行记录保存有效配置及允许的配置指纹、精确代码版本与适用的 tag、schema 与实现版本、数据集及分区修订、模型与前序状态 ID、数值环境及尝试日志。记录必须足以选择原始输入和状态。[Check]
- **禁止对数据集哈希。** 原始与派生数据集，包括行情、财务、特征和 Alpha 输出，均禁止内容哈希、校验和、逐行哈希和分区指纹。数据与状态快照使用显式不可变修订 ID、分区清单、schema 和来源／前序引用标识。不得把数据伪装成配置后哈希。本规则不禁止 Git 的代码版本标识。[Check / Review]
- 通过契约、行键唯一性、行数、时间覆盖、来源关系和验收测试中的定向内容对照验证数据。这些检查不提供密码学内容完整性保证。不要求每次运行都对完整历史逐字节比较或重新通读。[Check / Test]
- 只有输入修订、节点实现、schema、有效配置、模型和初始状态身份全部一致时才复用缓存。任何依赖变化都生成新缓存版本，绝不原地刷新已发布版本。参数集名称本身不能充当缓存键。[Check / Test]

- 通过发布能力的公开契约测试行为，不能只测内部辅助函数。匹配重试返回既有结果，lineage 冲突时拒绝，读取者不应得到混版的输出与状态。券商等远端动作须按实际 adapter 契约测试响应不明的情况，并在重发前对账；没有服务端语义支持，本地事务不能承诺远端恰好执行一次。[Test / Review]

## 7. 效率与内存

先按已声明的数值与决策契约证明优化正确，再接受性能收益。[Test]

1. **声明预算。** 分别记录目标规模的实际耗时、持久状态大小、峰值临时内存和相关通信成本。在具名环境运行 benchmark，超过已声明的退化阈值时检查失败。[Check / Test]
2. **区分历史成本。** 增量节点只读取已声明的新增数据、尾部窗口和充分状态，不重复扫描增长的历史。全历史训练或重训另行声明扫描复杂度、频率和预算，不承诺恒定成本。[Test / Review]
3. **限制工作集。** 为分块、加速器批次、worker 池和缓存设置字节或数量上限。按 lookback、活跃标的池、特征维度与状态大小说明内存增长。流式工作内存不随总历史增长；全历史阶段单独设置预算。不得宣称精确滚动状态与窗口或标的池规模无关。[Check / Test]
4. **只读必需内容。** 对列式存储使用 lazy scan，下推日期与列过滤。[Check / Test]
5. **按读取方式布局存储。** 声明主要读取键并据此分区。先暂存不可变写入，再原子提交 manifest 引用；只有存储后端保证所需原子性时才使用 rename。[Test / Review]
6. **先 profile 再优化。** 向量化或编译已测得的热点。逐数组选择精度，测量隐藏复制与 reshape 开销。[Test / Review]
7. **遵守耦合关系。** 禁止沿标的轴盲切横截面算子。声明合法分组和跨分片归约，保留所需运算顺序，并与未分片参考比较合并结果。先测量再更换硬件。[Check / Test]
8. **区分可重复性与等价性。** 固定输入、状态与数值环境时，同一实现的重跑必须确定。离散输出精确比较。不同实现或环境的浮点比较，须在测量前声明有依据的容差；仅在契约要求时强制 bitwise 一致。单独测试下游排名、阈值、约束、取整和订单决策；小数值误差不代表决策相同。[Test / Review]
9. **避免重复校验开销。** 复用已验证的不可变修订及其来源元数据。在声明的边界执行第 6 节校验，不增加重复全量扫描或数据集哈希。[Check / Test]

性能检查既看计算内核，也看模块之间的数据流。增加硬件或抽象前，先测量多余读取、复制、序列化和反复接口调用。如果接口迫使调用方采用低效用法，应改进接口，同时保留 PIT、状态和数值契约。这应用了[第 20 章的性能设计思路](https://cactus-proj.github.io/A-Philosophy-of-Software-Design-zh/ch20.html)。[Test / Review]

## 8. 从 MVP 到完整范围

每阶段交付可验证能力。保持兼容性，或显式版本化并迁移变化的契约；不要冻结错误的首版设计。记录尚未覆盖的范围。[Test / Review]

| 阶段 | 范围 | 完成标准 | 落实方式 |
|---|---|---|---|
| 1 | 最小非退化合成样本，覆盖全部阶段；标的数与日期足以表达横截面结构、预热和状态转换 | 与独立参考一致；PIT、状态与基本幂等检查通过 | Test |
| 2 | 小规模真实样本，覆盖全部阶段，在测试环境真实写入 | 与独立参考一致；切换、回滚与恢复演练通过 | Test |
| 3 | 完整标的池 | 耦合语义、耗时、状态和工作内存预算成立 | Test |
| 4 | 完整历史 | Batch、Backfill 和 Step 满足已声明的等价契约；完整规模预算成立 | Test |
| 5 | 生产 | 上线产物齐备；重写项目通过影子运行阶段 | Check / Test / Review |

横截面项目的首个样本包含多行业、停牌标的、缺失观测与相关市场日历缺口。空输入、单行、单标的仍作为边界测试，不能作为唯一的 MVP。[Test / Review]

各适用阶段遵守以下验证规则：

- 预期值来自手算、已知公式、独立实现或冻结版本的旧系统。不得从被测代码生成预期值，也不得在参考实现中悄悄复用存在争议的对齐逻辑。[Test / Review]
- 测试边界契约、节点行为和预期操作入口。真实 fixture 使用带来源记录的小规模只读样本，外部系统使用 fake。每条正确性规则都有放行与拒绝场景。[Test]
- 固定随机种子的合成数据覆盖标的生命周期、迟到或修订数据、日历缺口和状态恢复。修改预期值时须附书面理由并生成新的 fixture 版本。[Test / Review]
- 扰动决策之后才可用的输入，验证原决策不变。将重复可用性打标与错误边界输入列为拒绝场景。允许有界的输入或崩溃故障注入；不使用代码变异测试或多轮对抗评审循环。[Test / Review]
- 从第一个可复用的含状态切片开始，执行下列三项幂等场景。比较输出、状态、行键唯一性、权重汇总和发布次数；使用第 7 节数值契约，但不得放宽同键发布规则。[Test]

| 场景 | 必须观察到的结果 | 落实方式 |
|---|---|---|
| 同一决策日连跑两次，包含并发尝试 | 只有一份逻辑结果和一次已提交的状态转换；无重复行、权重或下游发布 | Test |
| 提交前崩溃，以及接收端已提交但本地尚未确认时崩溃，随后恢复 | 不出现输出与状态混版；重试先核对已提交状态，不重复发布或推进 | Test |
| 全量 Batch 对比分段 Batch 加逐日 Step、Backfill 和重复日期 | 相同预热、PIT 视图、来源关系及已声明数值契约下，重叠区间输出与状态一致 | Test |

- 快速测试集须满足耗时预算，每次 push 前执行。验收使用生产代表性规模，记录环境与精确集成版本。集成后不能仅使用 worker 分支的证据。区分已执行检查与仅规定未来实现的测试。[Check / Test]
- 按原则文档第 7 节选择最快的可行执行方式：小任务直接做；中型独立任务仅在并行收益超过协调成本时委派；大型或长周期工作使用持久化任务 DAG。任务 DAG 与平台计算 DAG、执行状态机分别定义。[Review]
- 持久化工作记录依赖状态、版本化输入、输出、检查点、重试规则和验收条件。使用可用的 workflow 执行可重复步骤、goal 保存长期目标、cron 在未来唤醒、带界限的 loop 推进迭代。Cron 不代表依赖已就绪；loop 必须有退出条件及迭代或时间预算。使用前确认能力可用，对重复唤醒去重，只报告“已调度”而不能当作“已完成”。协调慢于直接执行时减少并发。[Check / Test / Review]

- 每次交付可复用能力时，在验收测试之外检查设计。展示新 Alpha 如何复用平台、供应商变化如何限制在局部。检查调用方负担、重复知识、无意义的透传层和未记录的调用顺序。合并紧密耦合的代码如果能降低整体复杂度，就应考虑合并，同时保持公开契约兼容或显式版本化。不能用函数数量或行数目标替代这项审查。[Review]

## 9. 代码风格

- 遵循 Python 之禅，保持浅嵌套。函数应职责集中，并能结合上下文读懂；拆分应能封装完整机制或分离无关职责。不要只为满足行数限制，把一段数学计算拆成许多仅调用一次的包装函数。[Review]
- 注释简练，但解释不直观的数学与时间语义。`schemas/` 和量化算子允许多行 docstring；适用时说明张量轴序、单位、自由度与缺失值传播。不得为行数规则牺牲必要含义。[Check / Review]
- 参数和配置哈希仅按第 4、6 节使用；各层都执行数据集禁哈希规则。[Check]
- 仅在真实 I/O、应用入口或任务监督边界捕获异常，并声明恢复或报告策略。保留业务拒绝并记录失败；不得吞错或静默替换结果。[Test / Review]
- 项目形成稳定风格前指定参考仓库或模块。每条规则分配检查器、测试或审查人；尽早自动化机械规则，并记录检查的局限。[Check / Review]

实现重要模块之前，先写接口说明与调用示例。记录签名无法直接表达的行为、前提、单位、张量轴序、时间语义、副作用和失败情况。如果接口很难解释，应据此重新审视设计。这借鉴了[第 13 章关于有效注释的讨论](https://cactus-proj.github.io/A-Philosophy-of-Software-Design-zh/ch13.html)和[第 15 章“先写注释”](https://cactus-proj.github.io/A-Philosophy-of-Software-Design-zh/ch15.html)。原则文档第 2、7 至 9 节规定对应的边界、协调与审核要求；这些来自书中的设计方法用于补充量化正确性门禁。[Review]
